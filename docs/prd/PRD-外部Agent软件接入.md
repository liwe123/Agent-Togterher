# PRD：外部 Agent 软件接入与调度

> 类型：Requirement ｜ 状态：部分完成 ｜ 目标：把 `Cursor`、`Codex`、`Trae`、`Antigravity` 等外部 Agent 软件从「静态展示卡片」升级为可注册、可心跳、可分发任务、可回传结果的执行节点，并与现有任务编排器、工作区与实时状态流打通。
>
> 实施口径（2026-08-29 核对）：集成节点注册/心跳/调度基座（C-118 / C-129）、Cursor 与 Codex 桥接真实执行、群聊 `@` 外部节点派发（C-137）均已落地；**Antigravity / Trae 适配器仍为零实现**（桥接工厂仅注册 `cursor` / `codex`，见《代码与计划落地差距审查报告-20260828》§2.1）。

---

## 1. 背景与问题

当前系统中的 `Software Dock` 仅展示 6 个软件入口，点击后只是切换在线样式，并没有真实连接后端状态，也没有任务调度、心跳、结果回传能力。与此同时，项目已经具备以下基础能力：

- 任务编排器 `AgentOrchestrator`
- 持久化任务队列与独立 Worker
- 插件注册中心与工具热插拔
- WebSocket 实时事件总线
- 工作区与权限隔离

这些能力说明系统已经具备承接外部执行节点的基础，但缺少一层统一的「外部 Agent 软件接入」能力，用于把第三方 IDE / CLI / 桌面 Agent 工具纳入同一调度平面。

### 现存问题

1. **软件 Dock 只是静态面板**
   - 没有真实连接状态
   - 没有心跳与版本信息
   - 没有任务数与处理队列

2. **外部 Agent 软件没有统一协议**
   - Cursor、Codex、Trae、Antigravity 可能分别走 API、CLI、Bridge、桌面自动化
   - 系统缺少统一的适配层

3. **任务只能进入系统内置编排器**
   - 不能根据能力、工作区、负载或手动选择将任务派给外部软件

4. **状态不可观测**
   - 无法统一查看软件在线/离线、版本、最后心跳、当前任务、失败原因

---

## 2. 目标与非目标

### 2.1 目标

- G1：将外部 Agent 软件建模为可注册的执行节点，纳入统一控制面。
- G2：为每个节点提供状态、心跳、能力、版本、处理中的任务数等可观测信息。
- G3：支持将任务分发给指定节点或按能力自动选择节点。
- G4：节点执行结果能够回传到任务轨迹与消息流，并通过 WebSocket 实时更新前端。
- G5：支持按工作区隔离节点可见性与可用能力。
- G6：前端 `Software Dock` 从静态 UI 升级为动态数据驱动面板。
- G7：保持与现有任务编排器、插件注册中心、工具调用能力兼容。

### 2.2 非目标

- N1：不要求所有外部软件都使用同一实现方式；不同软件可以通过 API、CLI 或本地 Bridge 接入。
- N2：不要求在本期内实现对所有软件的深度桌面自动化控制。
- N3：不要求替换现有 LLM 接入层，LLM 仍通过 LiteLLM 管理。
- N4：不要求将外部 Agent 软件直接当作模型替代品；它们是执行节点，不是 LLM 本身。

## 3. 用户故事

- US1：作为工作区管理员，我希望看到每个 Agent 软件的在线状态、当前负载和最后心跳，以便判断是否可以派发任务。
- US2：作为调度者，我希望能把某个任务指定给 Cursor、Codex 或 Trae 这类节点执行，而不是只能交给系统内置 Agent。
- US3：作为开发者，我希望外部 Agent 软件通过统一协议接入系统，避免为每个工具单独开发一套页面和调度逻辑。
- US4：作为调试者，我希望能在任务详情页看到任务到底被哪个外部节点执行、执行了多久、是否失败、失败原因是什么。
- US5：作为平台管理员，我希望某个工作区只启用少数几个节点，并能按工作区隔离可见范围与执行权限。

## 4. 核心概念

### 4.1 外部 Agent 节点（Integration Node）

一个已注册的外部执行实体，可能对应：

- 本地 CLI 工具
- 桌面 IDE
- 本地 Bridge 服务
- 远程 API Agent

### 4.2 适配器（Adapter）

将外部软件的具体协议适配为系统统一接口的实现层。适配器负责：

- 连接与断开
- 心跳上报
- 任务分发
- 结果回传
- 错误转换

### 4.3 节点能力（Capabilities）

用于描述该软件可以处理什么类型的任务，例如：

- `code_edit`
- `terminal_run`
- `doc_write`
- `review`
- `browser_automation`

### 4.4 调度策略（Dispatch Policy）

任务应该派发给哪个节点的规则，可包括：

- 手动指定
- 依据能力匹配
- 依据负载最小化
- 依据工作区白名单
- 失败回退到其他节点

---

## 5. 方案概述

本需求新增一层「外部 Agent 软件接入层」，位于前端展示与后端编排器之间：

- 前端 `Software Dock` 从后端拉取真实节点信息。
- 后端维护节点注册、状态、能力、心跳和任务分发记录。
- 通过统一的适配器接口，支持不同软件的接入实现。
- 任务编排器能够按策略把任务派发给指定外部节点。
- WebSocket 负责实时推送节点状态变化与任务执行事件。

## 7. 接入模式

### 7.1 API 模式

适用于本身提供开放接口的软件：

- 后端直接调用其 HTTP API
- 由适配器处理鉴权、重试、超时与结果标准化

### 7.2 CLI 模式

适用于提供命令行能力的软件：

- 后端或独立 Bridge 启动子进程
- 通过 stdin/stdout 或 JSON 文件交互
- 解析结构化输出并回写任务结果

### 7.3 Bridge 模式

适用于桌面应用或本地工具：

- 在本地运行一个 Bridge 服务
- 前端只对后端负责
- 后端通过 Bridge 管理连接与任务流

### 7.4 自动化模式

适用于没有公开 API/CLI 的工具：

- 通过可控的自动化层完成有限交互
- 仅作为兜底，不作为主接入方式

## 8. 数据设计

### 8.1 建议新增模型

- `integration_nodes`：外部 Agent 节点主表
- `integration_heartbeats`：节点心跳记录表（可选）
- `integration_dispatches`：任务派发记录表（可选）

### 8.2 建议字段

`integration_nodes` 典型字段：

- `id`
- `workspace_id`
- `name`
- `provider`（cursor/codex/trae/antigravity/custom）
- `mode`（api/cli/bridge/automation）
- `status`（online/offline/connecting/error/busy）
- `version`
- `capabilities_json`
- `endpoint`
- `last_heartbeat_at`
- `current_task_count`
- `max_concurrency`
- `created_at`
- `updated_at`

### 8.3 决策建议

- 本期优先落一个主表 `integration_nodes`，满足 Dock 展示与调度。
- 心跳与派发日志可先复用现有事件/审计能力，后续再视数据量决定是否拆分明细表。

## 9. 后端实现建议

### 9.1 节点注册中心

新增后端服务层，职责包括：

- 创建和更新节点元数据
- 维护节点健康状态
- 记录最后心跳
- 根据能力/负载筛选可用节点

### 9.2 适配器接口

统一定义适配器接口，例如：

- `connect()`
- `disconnect()`
- `heartbeat()`
- `dispatch_task()`
- `collect_result()`
- `get_capabilities()`

### 9.3 调度流程

1. 用户在前端选择一个节点，或系统根据策略自动选择。
2. 后端创建派发记录。
3. 通过适配器把任务发给对应软件。
4. 适配器不断上报状态与进度。
5. 结果写回任务、消息流和轨迹。

### 9.4 失败处理

- 节点超时未心跳，自动标记离线。
- 任务失败可回退到系统内置编排器或其他节点。
- 派发过程需记录错误原因，避免黑盒失败。

## 10. 前端体验需求

### 10.1 Software Dock

从静态展示改为动态卡片，展示：

- 节点名称
- 连接状态
- 接入模式
- 当前任务数
- 最后心跳
- 能力标签

### 10.2 节点详情

点击卡片后展示：

- 节点配置摘要
- 运行状态
- 最近派发任务
- 错误日志
- 重新连接 / 重新派发入口

### 10.3 任务关联视图

任务详情页中需展示：

- 任务由哪个节点执行
- 节点执行耗时
- 执行结果
- 是否发生回退或重试

## 11. 安全与权限

- 节点接入必须绑定工作区。
- 节点只能看到授权范围内的任务。
- 节点凭证、token、密钥必须脱敏存储与展示。
- 节点调用应使用统一超时、重试与熔断策略。

---

## 12. 验收标准（AC）

- AC1：前端 `Software Dock` 不再依赖静态数组，而是从后端动态加载节点信息。
- AC2：系统可以注册至少一种外部 Agent 节点并展示在线状态。
- AC3：节点心跳、离线、忙碌等状态可实时更新。
- AC4：任务可以被派发到指定节点并回传执行结果。
- AC5：任务详情页能看到节点执行信息与历史派发记录。
- AC6：工作区隔离生效，不同工作区看不到未授权节点。
- AC7：前端与后端测试通过，新增功能无回归。

## 14. 风险与待定项

### 风险

- 不同软件协议差异大，适配器复杂度高。
- 某些工具没有稳定 API，桥接与自动化方案脆弱。
- 节点状态与任务状态需要一致性设计，否则容易出现“显示在线但实际不可用”。

### 待定项

- 首批接入软件优先级。
- 是否需要独立的本地 Bridge 进程。
- 是否允许一个节点同时执行多个任务。
- 是否将节点能力暴露给任务模板或工作流引擎。

## 15. 与现有系统的关系

本需求基于现有以下能力演进：

- `Software Dock` 现有展示位
- `AgentOrchestrator` 任务编排器
- `plugins` 插件注册中心
- `task_queue_items` 持久化任务队列
- `WebSocket` 实时事件通道

它补齐的是：**让外部 Agent 软件真正成为可调度、可观测、可回传的执行节点**。

---

## 16. 结论

这不是一次简单的 UI 改造，而是一次把外部 Agent 软件纳入系统执行平面的平台能力升级。核心原则是：

- 统一建模
- 统一状态
- 统一调度
- 统一回传
- 统一观测

只有这样，`Software Dock` 才会从“展示面板”变成“调度中枢”。
