# PRD：单任务上下文连续性与执行过程可视化

> 类型：新需求（Requirement）｜状态：已完成｜目标：让模型在**同一条任务**的整个执行过程中始终看到最新、完整的结构化执行上下文与工具调用链路，避免上下文中断、阶段失忆、失败后重复探索，同时让执行过程对前端与调试者**可见、可回放、可恢复**。
>
> 来源：本文档由 `PRD-单任务上下文连续性保障.md`（提交 70e53ee / C-073）与 `PRD-任务执行过程可视化与工具调用追踪.md`（提交 8e22c25 / C-074）于 2026-08-10 合并而成。前者为上游抽象目标，后者为落地实现方案，两者本质描述同一能力，故合并为单一 PRD。

---

## 1. 背景与问题

当前项目已具备任务编排能力：任务会被 `AgentOrchestrator` 领取，按单 Agent 或多 Agent 流程执行，并将 `TaskStep`、`ModelCall`、`Message`、`TaskStatus` 等信息落库与广播。

但从「单条任务内部」和「模型执行视角」看，仍有明显缺口：

1. **模型输入依赖临时变量**
   - 现有实现里，模型调用主要依赖 `task.description`、`extra_messages` 和工具循环中的临时 `history`。
   - 一旦执行阶段切换、任务重试、Agent 切换，临时上下文就会丢失。

2. **任务轨迹没有统一回灌机制**
   - 任务步骤、模型调用、工具结果虽然会落库，但不会自动重新拼装成下一轮模型可直接消费的上下文。
   - 模型看不到「之前已经做过什么、得出了什么结论、遇到了什么错误」。

3. **工具调用链路对模型不够显式**
   - 工具调用是 `tool_calls -> execute_tool -> tool` 回合制闭环，但模型下一次调用依赖的是临时 `history`。
   - 当任务跨多个阶段、跨多个 Agent、甚至跨重试恢复时，缺少一个稳定、结构化、可追踪的「思考/执行轨迹视图」。

4. **多 Agent 场景中的阶段衔接不稳定**
   - Manager、Worker、QA、Final 各阶段顺序执行，目前更多依赖各阶段单独传参。
   - 如果某个阶段失败后恢复，模型容易重新探索或重复执行。

### 本轮要解决的问题

- 让模型在**同一条任务**里，每次继续执行时都能看到完整且最新的结构化上下文：任务目标、当前阶段、已完成步骤、工具调用结果、关键约束和失败原因。
- 让工具调用结果、阶段性结论、失败原因都能被下一轮模型调用稳定继承，形成可回放的显式链路。
- 让任务执行从「散点式历史」升级为「统一的任务级上下文流」，前端与后端都能展示这条链路，便于调试、审计、复盘和二次调用。

> 说明：本需求关注的是**任务级结构化上下文连续性与执行轨迹可见性**，不是把模型内部不可见的原始思维草稿直接暴露给用户。

## 2. 目标与非目标

### 2.1 目标

- G1：在**同一条任务**中，模型每次调用前都能读取到最新的任务上下文（任务目标、当前阶段、已完成步骤、工具结果、失败信息、待办项）。
- G2：工具调用形成连续可回放链路：`模型输出 -> 工具调用 -> 工具结果 -> 下一轮模型输入`。
- G3：任务执行过程形成统一的「执行轨迹」，可在数据库、WebSocket 和前端详情页中查看。
- G4：多 Agent 场景中，Manager / Worker / QA / Final 各阶段都能继承前序阶段的结论、约束与轨迹，而不是只看到原始任务描述。
- G5：任务失败、重试、恢复后，模型依然能拿到之前已完成步骤、上下文摘要与错误原因，减少重复劳动。
- G6：上下文超长时，系统自动摘要和裁剪，但关键状态不丢失。

### 2.2 非目标

- N1：不把模型内部完整隐式推理草稿（原始 chain-of-thought）作为产品内容展示或产品依赖。
- N2：不要求一次性改造成多进程消息队列或分布式工作流引擎。
- N3：不要求把所有历史消息无差别塞进模型上下文，需通过摘要与裁剪策略控制长度。
- N4：不要求所有任务都启用工具链，纯文本任务仍应保持简洁路径。

## 3. 用户故事

- US1：作为用户，我希望任务运行过程中，模型不会「忘记」前面刚刚做过的事情，也能看到「模型为什么继续这样做」，而不是只有最终答案。
- US2：作为用户，我希望工具执行后的结果能影响后续模型决策，并能看到模型调用过哪些工具、工具返回了什么、这些结果如何影响后续步骤，而不是只作为日志保留。
- US3：作为调试者，我希望在任务失败后，能看到失败前的上下文、工具结果和模型最后一次实际输入，快速定位问题。
- US4：作为系统，我希望在重试或恢复任务时，模型能读取到已有执行轨迹与上下文摘要，接着之前的上下文继续，而不是重新从头开始。
- US5：作为多 Agent 编排系统，我希望 Manager、Worker、QA、Final 每一阶段都能共享并继承同一条任务轨迹。

## 4. 核心概念

### 4.1 任务级上下文（Task-Level Context）

一条任务在执行过程中持续维护的上下文对象，包含：

- 任务目标
- 当前阶段
- 已完成步骤
- 最近模型输出
- 工具调用记录
- 工具输出结果
- 失败原因
- 重试原因
- 当前约束与待办项

### 4.2 上下文连续性（Context Continuity）

指模型在同一条任务中，每次重新调用时都能获得上一轮执行中积累的关键状态，而不是依赖某个函数局部变量。

### 4.3 执行轨迹（Execution Trace）

任务从创建到完成的可追踪链路，包含任务目标、当前阶段、已执行步骤、模型输入/输出摘要、工具调用记录、工具输出结果、失败原因与恢复动作。

### 4.4 结构化执行上下文（Structured Execution Context）

在每次调用模型时注入的一段结构化上下文（而非纯拼接的自由文本），建议由以下部分组成：

- `task_summary`：任务摘要
- `current_stage`：当前阶段（manager_plan / worker_execute / review_results / final_summary 等）
- `completed_steps`：已完成步骤列表
- `recent_tool_results`：最近 N 条工具结果
- `open_issues`：未解决问题
- `constraints`：约束与注意事项
- `failure_notes`：失败原因或重试原因

### 4.5 轨迹摘要（Trace Summary）

当历史过长时，由后端将较早内容压缩成摘要，替代长历史，保证模型继续执行时仍能看到关键决策与失败信息，避免 prompt 失控。

## 5. 方案概述

在现有任务编排之上新增一层「任务轨迹层/上下文构建器」，位于任务数据层和模型调用层之间：

- 任务步骤、模型调用、工具结果继续落库。
- 每次模型调用前，Orchestrator 从数据库拼装出**结构化执行上下文**并回灌给模型。
- 模型调用后，结果、工具调用、工具输出继续写入轨迹。
- 前端任务详情页新增「执行轨迹」视图，展示计划、工具、摘要、阶段、失败链路，帮助调试与复盘。

## 7. 任务流转设计

### 7.1 单 Agent 任务

1. 任务进入 `PENDING`，Orchestrator 领取任务并生成任务级上下文。
2. 模型接收：任务目标 + 当前阶段 + 历史步骤 + 工具结果摘要。
3. 若模型发起工具调用：
   - 记录工具名和参数
   - 执行工具
   - 将工具结果写入任务上下文/轨迹
   - 再次把更新后的轨迹喂给模型
4. 模型给出最终结果后，保存最终结果和完整轨迹摘要，任务结束。

### 7.2 多 Agent 任务

1. Manager 先读取任务目标与已有轨迹，生成任务拆解计划。
2. Worker 执行前读取：任务摘要、Manager 计划、当前子任务、上一阶段结果、相关工具输出。
3. QA 阶段读取所有 Worker 结果与工具链路，生成审核意见。
4. Final 阶段读取计划、执行结果和审核意见，生成最终汇总。
5. 每个阶段结束后，任务上下文/轨迹都要更新一次，供下一阶段继承。

### 7.3 失败与恢复

1. 某一步失败时，记录失败前上下文和错误原因。
2. 任务恢复或重试时，优先加载任务上下文摘要 + 最近关键步骤。
3. 下一轮模型调用必须明确看到失败原因，避免重复失败。

## 8. 数据设计

### 8.1 可复用现有表

现有对象继续使用：

- `Task`
- `TaskStep`
- `ModelCall`
- `Message`
- `Agent`

### 8.2 可选新增概念

可以选择新增任务上下文/轨迹聚合层：

- `TaskContext` / `TaskTrace`：任务上下文（轨迹）主表，保存版本、摘要、阶段、最后更新时间
- `TaskContextEvent` / `TaskTraceEvent`：上下文（轨迹）变化事件，如步骤完成、工具调用、摘要刷新、失败恢复

### 8.3 建议字段

如果复用 `TaskStep` 或新建上下文表，可考虑加入：

- `context_type` / `trace_type`：step / tool_call / tool_result / summary / failure / recovery
- `context_snapshot`：本轮模型调用前的上下文快照
- `visible_summary`：前端展示摘要
- `internal_summary`：给模型用的结构化摘要

### 8.4 决策记录

**已决策（2026-08-10 落地核对）**：暂不新增独立上下文/轨迹表，**复用现有 `Task + TaskStep + ModelCall` 实时拼装**（`tasks.py:_task_detail` 调 `build_trace_artifact` 动态组装，不落库）。该选择可维护性稍弱，但避免表结构膨胀；若后续轨迹数据量增大，再评估落库。

## 9. 前端体验需求

### 9.1 任务详情页

新增「执行轨迹」模块，分三层展示：

- **阶段时间线**：manager_plan / worker_execute / review_results / final_summary
- **工具调用链**：模型请求 → 工具参数 → 工具返回 → 是否影响后续决策
- **上下文摘要**：模型下一次调用时实际看到的摘要内容

### 9.2 运行态展示

任务运行时应能实时看到：

- 当前阶段
- 最近一轮模型输入摘要
- 最近一轮工具输出
- 当前是否在等待工具结果
- 是否发生过失败和重试，失败时的最后上下文

### 9.3 视图分层

- 普通用户默认看到摘要版，保证简洁。
- 调试/开发者模式可展开完整结构化上下文，用于排障。
- 敏感字段默认脱敏。

## 10. 后端实现建议

### 10.1 上下文构建器

新增一个上下文构建模块，职责包括：

- 查询任务最近步骤、模型调用、消息和工具结果
- 按阶段拼装结构化上下文
- 对长历史进行摘要与裁剪
- 过滤敏感信息

### 10.2 调用入口改造

每次调用模型前，不再只传 `task.description`，而是传：

- system prompt
- 任务摘要
- 当前阶段
- 最近步骤
- 工具结果摘要
- 失败原因
- 最新待办项

### 10.3 工具闭环

工具调用完成后应立即写回任务上下文，并作为下一轮模型输入的一部分，每轮记录：工具名、参数、调用时间、返回结果、返回结果摘要、结果是否被模型采纳。

### 10.4 上下文压缩

建议使用两级压缩：

- **短期上下文**：保留最近 N 个步骤与工具调用原文
- **长期摘要**：保留更早阶段的结构化摘要

## 11. 安全与合规

- 不展示也不落库敏感密钥明文。
- 工具输出中的敏感内容需脱敏后再进入用户可见视图。
- 模型可见上下文中应避免暴露内部凭据。
- 若后续扩展「思考过程」展示，应只展示产品定义的结构化上下文/执行轨迹，不展示未经约束的内部推理草稿。

---

## 12. 验收标准（AC）

- AC1：同一条任务中，模型每次继续执行时都能读取到上一轮的结构化上下文。
- AC2：工具调用结果能够影响下一轮模型输出，工具调用链路可在任务详情页完整展开（工具名、参数、结果、后续影响），而不是只作为日志保存。
- AC3：多 Agent 场景中，各阶段共享同一条任务轨迹，不会丢失前序步骤。
- AC4：任务失败后重试，模型可读取失败前上下文与错误原因。
- AC5：上下文过长时，摘要与裁剪机制生效，任务仍可继续执行。
- AC6：前端任务详情页可实时查看任务上下文/轨迹变化，无需手动刷新页面。

## 14. 风险与待定项

### 风险

- 上下文/轨迹过长导致模型输入膨胀。
- 工具输出过多导致前端和数据库膨胀、展示噪音。
- 如果直接展示所有内部过程，可能引起安全和体验问题。

### 待定项

- 摘要采用规则压缩还是模型压缩（当前为规则/长度裁剪）。
- 用户默认视图是否显示完整工具参数。
- 是否为不同 Agent 设定不同的上下文/轨迹可见粒度。

- `backend/app/schemas/task.py` 已有任务步骤和模型调用的返回结构。

本 PRD 补齐的是：**把这些分散的历史信息，统一变成下一轮模型可直接消费的任务级上下文，并在前端形成一条清晰的轨迹视图**。

trace 为**实时计算**（`tasks.py:_task_detail` 调 `build_trace_artifact` 组装，不落库），未新增 `TaskTrace`/`TaskTraceEvent` 表，复用 `Task/TaskStep/ModelCall`。

## 17. 结论

单任务内的上下文不中断，关键不是让模型「记住一切」，而是让系统在每次调用前都能**重新构建正确的任务级上下文**，并把任务执行过程工程化为一条**可见、可追踪、可回灌、可恢复**的执行轨迹。

只要做到：

- 步骤可追踪
- 工具结果可回灌
- 失败原因可继承
- 历史可摘要、可裁剪
- 阶段之间共享同一条轨迹

那么模型在同一条任务里就能持续「看见自己正在做什么」，上下文就不会轻易断掉。
