# PRD：单任务上下文连续性保障

> 类型：新需求（Requirement）｜状态：草案｜目标：让模型在**同一条任务**的整个执行过程中，始终能看到上一阶段的结构化上下文、工具调用结果与失败信息，避免上下文中断。

---

## 1. 背景与问题

当前项目已经具备任务编排、步骤记录、模型调用日志和工具调用闭环：`AgentOrchestrator` 会领取任务，按单 Agent 或多 Agent 流程执行，并将 `TaskStep`、`ModelCall`、`Message` 等信息落库与广播。

但在**单条任务内部**，上下文连续性仍有几个明显问题：

1. **模型输入依赖临时变量**
   - 现有实现里，模型调用主要依赖 `task.description`、`extra_messages` 和工具循环中的临时 `history`。
   - 一旦执行阶段切换、任务重试、Agent 切换，临时上下文就会丢失。

2. **任务轨迹没有统一回灌机制**
   - 任务步骤、模型调用、工具结果虽然会落库，但不会自动重新拼装成下一轮模型可直接消费的上下文。
   - 模型看不到“之前已经做过什么、得出了什么结论、遇到了什么错误”。

3. **多 Agent 场景中的阶段衔接不稳定**
   - Manager、Worker、QA、Final 各阶段是顺序执行的，但目前更多依赖各阶段单独传参。
   - 如果某个阶段失败后恢复，模型容易重新探索或重复执行。

### 本轮要解决的问题

- 让模型在**同一条任务**里，每次继续执行时都能看到完整且最新的结构化上下文。
- 让工具调用结果、阶段性结论、失败原因都能被下一轮模型调用稳定继承。
- 让任务执行从“散点式历史”升级为“统一的任务级上下文流”。

> 说明：本需求关注的是**任务级结构化上下文连续性**，不是把模型内部不可见的原始思维草稿直接暴露给用户。

---

## 2. 目标与非目标

### 2.1 目标

- G1：在同一条任务中，模型每次调用前都能读取到最新的任务上下文。
- G2：工具调用形成连续链路：`模型输出 -> 工具调用 -> 工具结果 -> 下一轮模型输入`。
- G3：任务执行过程中，Manager / Worker / QA / Final 各阶段都能继承前序阶段的结论与约束。
- G4：任务失败、重试、恢复后，模型依然能拿到之前已完成步骤与错误原因。
- G5：上下文超长时，系统自动摘要和裁剪，但关键状态不丢失。

### 2.2 非目标

- N1：不要求把模型内部完整隐式推理草稿作为产品内容展示。
- N2：不要求一次性改成分布式工作流引擎或消息队列系统。
- N3：不要求把所有历史消息无差别塞进模型上下文。
- N4：不要求所有任务都启用工具链，纯文本任务仍应保持简洁。

---

## 3. 用户故事

- US1：作为用户，我希望任务运行过程中，模型不会“忘记”前面刚刚做过的事情。
- US2：作为用户，我希望工具执行后的结果能影响后续模型决策，而不是只作为日志保留。
- US3：作为调试者，我希望在任务失败后，能看到模型最后一次实际输入了什么上下文。
- US4：作为系统，我希望任务恢复后，模型能接着之前的上下文继续，而不是重新从头开始。
- US5：作为多 Agent 编排系统，我希望每个阶段都能共享同一份任务轨迹。

---

## 4. 核心概念

### 4.1 任务级上下文（Task-Level Context）

一条任务在执行过程中持续维护的上下文对象，建议包含：

- 任务目标
- 当前阶段
- 已完成步骤
- 最近模型输出
- 工具调用记录
- 工具输出结果
- 失败原因
- 重试原因
- 当前约束与待办项

### 4.2 上下文连续性（Context Continuity）

指模型在同一条任务中，每次重新调用时都能获得上一轮执行中积累的关键状态，而不是依赖某个函数局部变量。

### 4.3 轨迹摘要（Trace Summary）

当上下文过长时，由后端将较早内容压缩成摘要，保留关键信息，避免 prompt 失控。

---

## 5. 方案概述

本需求建议在现有任务编排之上新增一层“任务上下文构建器”：

- 任务步骤、模型调用、工具结果继续落库。
- 每次模型调用前，从数据库拼装任务级上下文。
- 工具调用结果写入上下文后，再喂给下一轮模型调用。
- 前端任务详情页展示同一份上下文轨迹，帮助调试与复盘。

## 7. 任务流转设计

### 7.1 单 Agent 任务

1. 任务进入 `PENDING`。
2. Orchestrator 领取任务并生成任务级上下文。
3. 模型接收：任务目标 + 当前阶段 + 历史步骤 + 工具结果摘要。
4. 若模型发起工具调用：
   - 保存工具调用参数
   - 执行工具
   - 将工具结果写入任务上下文
   - 重新调用模型
5. 任务结束时，保存最终结果和完整轨迹摘要。

### 7.2 多 Agent 任务

1. Manager 先读取任务上下文并生成计划。
2. Worker 执行前读取：任务目标、Manager 计划、当前子任务、历史结果。
3. QA 阶段读取全部 Worker 结果和工具链路。
4. Final 阶段读取计划、执行结果和审核意见，生成最终汇总。
5. 每个阶段结束后，任务上下文都要更新一次，供下一阶段继承。

### 7.3 失败与恢复

1. 某一步失败时，记录失败前上下文和错误原因。
2. 任务恢复或重试时，优先加载任务上下文摘要。
3. 下一轮模型调用必须明确看到失败原因，避免重复失败。

## 8. 数据设计建议

### 8.1 可复用现有表

现有表可以继续使用：

- `Task`
- `TaskStep`
- `ModelCall`
- `Message`
- `Agent`

### 8.2 建议新增概念

可以选择新增任务上下文聚合层：

- `TaskContext`：任务当前上下文快照、版本、摘要、最后更新时间
- `TaskContextEvent`：上下文变化事件，如步骤完成、工具调用、摘要刷新、失败恢复

如果暂不新增表，也可以先基于现有 `TaskStep + ModelCall + Message` 拼装上下文，但后续可维护性较弱。

### 8.3 建议字段

如果复用 `TaskStep` 或新建上下文表，可考虑加入：

- `context_type`：step / tool_call / tool_result / summary / failure / recovery
- `context_snapshot`：本轮模型调用前的上下文快照
- `visible_summary`：前端展示摘要
- `internal_summary`：给模型用的结构化摘要

## 9. 前端体验需求

### 9.1 任务详情页

新增“任务上下文”模块，分层展示：

- 当前阶段
- 最新摘要
- 已完成步骤
- 工具调用链路
- 失败与恢复记录

### 9.2 运行态展示

任务运行时应能看到：

- 当前模型正在看什么上下文
- 最近一次工具输出
- 当前是否等待工具结果
- 是否发生过失败和重试

### 9.3 视图分层

- 普通用户默认看到摘要版
- 调试模式可展开完整上下文
- 敏感字段默认脱敏

---

## 10. 后端实现建议

### 10.1 上下文构建器

建议新增一个上下文构建模块，职责包括：

- 查询任务最近步骤、模型调用、消息和工具结果
- 拼装任务级上下文
- 对长历史进行摘要与裁剪
- 过滤敏感信息

### 10.2 调用入口改造

每次调用模型前，不再只传 `task.description`，而是传：

- system prompt
- 任务摘要
- 当前阶段
- 最近步骤
- 工具结果摘要
- 失败原因
- 最新待办项

### 10.3 工具闭环

工具调用完成后，应立即写回任务上下文，并作为下一轮模型输入的一部分。

---

## 11. 安全与合规

- 不展示也不落库敏感密钥明文。
- 工具输出中的敏感内容需脱敏后再进入用户可见视图。
- 模型可见上下文中应避免暴露内部凭据。
- 若后续扩展“思考过程”展示，应只展示产品定义的结构化上下文，不展示未经约束的内部推理草稿。

---

## 12. 验收标准（AC）

- AC1：同一条任务中，模型每次继续执行时都能读取到上一轮的上下文。
- AC2：工具调用结果能够影响下一轮模型输出，而不是只作为日志保存。
- AC3：任务失败后重试，模型可读取失败前上下文与错误原因。
- AC4：多 Agent 场景中，各阶段共享同一条任务轨迹。
- AC5：上下文过长时，摘要与裁剪机制生效，任务仍可继续执行。
- AC6：前端任务详情页可实时查看任务上下文变化，无需刷新。

## 14. 风险与待定项

### 风险

- 上下文过长导致模型输入膨胀。
- 工具输出过多导致展示噪音和存储膨胀。
- 如果直接展示所有内部过程，可能引起安全和体验问题。

### 待定项

- 是否新增独立任务上下文表，还是先沿用现有表拼装。
- 摘要采用规则压缩还是模型压缩。
- 用户默认是否显示完整工具参数。
- 是否为不同 Agent 设定不同的上下文可见粒度。

## 15. 与现有系统的关系

本需求建立在当前已有能力之上：

- `backend/app/core/orchestrator.py` 已负责任务编排、步骤记录、模型调用和工具循环。
- `backend/app/schemas/task.py` 已有任务步骤和模型调用的返回结构。
- `backend/app/api/v1/endpoints/tasks.py` 已能返回任务详情、步骤和模型调用。

本 PRD 需要补齐的是：**把这些分散的历史信息，统一变成下一轮模型可直接消费的任务级上下文**。

---

## 16. 结论

单任务内的上下文不中断，关键不是让模型“记住一切”，而是让系统在每次调用前都能**重新构建正确的任务级上下文**。

只要做到：

- 步骤可追踪
- 工具结果可回灌
- 失败原因可继承
- 历史可摘要、可裁剪
- 阶段之间共享同一条轨迹

那么模型在同一条任务里就能持续“看见自己正在做什么”，上下文就不会轻易断掉。
