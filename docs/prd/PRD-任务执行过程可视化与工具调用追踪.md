# PRD：任务执行过程可视化与工具调用追踪

> 类型：新需求（Requirement）｜状态：草案｜目标：让模型在执行任务时看到结构化的执行过程、工具调用链路和阶段性结果，而不是仅依赖单轮最终输出。

---

## 1. 背景与问题

当前项目已经具备任务编排能力：任务会被 `AgentOrchestrator` 领取，按单 Agent 或多 Agent 流程执行，并将 `TaskStep`、`ModelCall`、`Message`、`TaskStatus` 等信息落库与广播。

但从“模型执行”的角度看，仍存在两个缺口：

1. **模型在下一轮调用时，无法稳定看到上一轮的执行中间态**
   - 例如 Manager 拆解出的计划、Worker 的工具结果、QA 的审核意见、历史失败原因等。
   - 当前虽然部分信息会写入数据库和消息流，但没有形成统一的“执行上下文回灌”机制。

2. **工具调用链路对模型本身不够显式**
   - 现在工具调用是 `tool_calls -> execute_tool -> tool` 回合制闭环，但模型下一次调用时，依赖的是临时 `history`。
   - 当任务跨多个阶段、跨多个 Agent、甚至跨重试恢复时，模型缺少一个稳定、结构化、可追踪的“思考/执行轨迹视图”。

### 本轮要解决的问题

- 让模型在每次继续执行任务时，都能看到**当前任务的执行计划、已完成步骤、工具调用结果、关键约束和失败原因**。
- 让任务执行过程从“隐式上下文”升级为“显式链路”。
- 让前端和后端都能展示这条链路，便于调试、审计、复盘和二次调用。

> 说明：本需求关注的是**结构化执行轨迹与工具调用可见性**，不是把模型内部不可见的原始思维草稿直接暴露给用户。

---

## 2. 目标与非目标

### 2.1 目标

- G1：模型在每次任务推进时，都能读取到上一阶段的结构化上下文，包括：任务目标、当前阶段、已完成步骤、工具结果、失败信息、待办项。
- G2：任务执行过程形成统一的“执行轨迹”，可在数据库、WebSocket 和前端详情页中查看。
- G3：工具调用不只是执行一次，而是形成可回放的链路：`model -> tool_call -> tool_result -> next model call`。
- G4：多 Agent 场景中，Manager / Worker / QA / Final 各阶段都能继承前一阶段的轨迹，而不是只看到原始任务描述。
- G5：任务重试、失败恢复、重新领取后，模型能够拿到已完成的上下文摘要，减少重复劳动。

### 2.2 非目标

- N1：不强制展示模型内部完整隐式推理草稿，不把未结构化的原始 chain-of-thought 作为产品依赖。
- N2：不要求一次性改造成多进程消息队列或分布式工作流引擎。
- N3：不要求所有历史内容无限制灌入模型上下文，需通过摘要与裁剪策略控制长度。
- N4：不把所有任务都改成工具驱动，单纯文本回答任务仍可保持简洁路径。

---

## 3. 用户故事

- US1：作为用户，我希望任务执行过程中能看到“模型为什么继续这样做”，而不是只有最终答案。
- US2：作为用户，我希望能看到模型调用过哪些工具、工具返回了什么、这些结果如何影响后续步骤。
- US3：作为调试者，我希望在任务失败后能快速看到失败前的上下文、工具结果和最后一轮模型输入。
- US4：作为系统，我希望在重试或恢复任务时，模型能读取到已有执行轨迹，避免重复探索。
- US5：作为多 Agent 编排系统，我希望 Manager、Worker、QA、Final 每一阶段都能继承同一条任务轨迹。

---

## 4. 核心概念

### 4.1 执行轨迹（Execution Trace）

任务从创建到完成的可追踪链路，包含：

- 任务目标
- 当前阶段
- 已执行步骤
- 模型输入/输出摘要
- 工具调用记录
- 工具输出结果
- 失败原因与恢复动作

### 4.2 结构化执行上下文（Structured Execution Context）

在每次调用模型时注入的一段结构化上下文，而不是纯拼接的自由文本。建议由以下部分组成：

- `task_summary`：任务摘要
- `current_stage`：当前阶段（manager_plan / worker_execute / review_results / final_summary 等）
- `completed_steps`：已完成步骤列表
- `recent_tool_results`：最近 N 条工具结果
- `open_issues`：未解决问题
- `constraints`：约束与注意事项
- `failure_notes`：失败原因或重试原因

### 4.3 轨迹摘要（Trace Summary）

当历史过长时，由后端压缩生成的摘要，用于替代长历史，保证模型继续执行时仍能看到关键信息。

---

## 5. 方案概述

本需求建议新增一个“任务轨迹层”，位于任务数据层和模型调用层之间：

- 任务步骤、模型调用、工具结果继续落库。
- 每次模型调用前，Orchestrator 从数据库拼装出**结构化执行上下文**。
- 模型调用后，结果、工具调用、工具输出继续写入轨迹。
- 前端任务详情页新增“执行轨迹”视图，展示计划、工具、摘要、阶段、失败链路。

## 7. 任务执行链路设计

### 7.1 单 Agent 链路

1. 任务被领取。
2. 后端构造结构化执行上下文。
3. 模型收到：任务目标 + 当前阶段 + 历史步骤 + 工具结果摘要。
4. 若模型发起 tool call，则：
   - 记录工具名和参数
   - 执行工具
   - 将工具结果写入轨迹
   - 再次把更新后的轨迹喂给模型
5. 模型给出最终结果后，轨迹结束。

### 7.2 多 Agent 链路

1. Manager 先读取任务目标与已有轨迹。
2. Manager 生成任务拆解计划。
3. Worker 执行前读取：
   - 任务摘要
   - Manager 计划
   - 当前子任务
   - 上一阶段结果
   - 相关工具输出
4. QA 阶段读取所有 Worker 结果与工具链路。
5. Final 阶段读取计划、结果、审核意见，生成最终汇总。

### 7.3 失败与重试链路

1. 某一阶段失败时，记录失败原因和失败前上下文。
2. 恢复后，系统优先恢复“轨迹摘要 + 最近关键步骤”。
3. 下一轮模型调用必须看到失败原因，以便避免重复失败。

## 8. 数据设计建议

### 8.1 可复用现有表

现有的以下对象可以继续使用：

- `Task`
- `TaskStep`
- `ModelCall`
- `Message`
- `Agent`

### 8.2 建议新增的轨迹概念

可选新增一个轨迹聚合层，例如：

- `TaskTrace`：任务轨迹主表，保存轨迹版本、摘要、阶段、最后更新时间
- `TaskTraceEvent`：轨迹事件表，保存步骤、工具调用、摘要刷新、失败恢复等事件

如果暂时不新增表，也可以先基于现有 `TaskStep + ModelCall + Message` 拼装轨迹，但后续可维护性会较弱。

### 8.3 建议新增字段

可考虑在 `TaskStep` 或新表中增加：

- `trace_type`：step / tool_call / tool_result / summary / failure / recovery
- `context_snapshot`：本轮调用前的上下文快照
- `visible_summary`：前端展示摘要
- `internal_summary`：给模型用的结构化摘要

## 9. 前端体验需求

### 9.1 任务详情页

增加一个“执行轨迹”区域，分三层：

- **阶段时间线**：manager_plan / worker_execute / review_results / final_summary
- **工具调用链**：模型请求 → 工具参数 → 工具返回 → 是否影响后续决策
- **上下文摘要**：模型下一次调用时实际看到的摘要内容

### 9.2 运行态展示

在任务运行中，前端应实时显示：

- 当前阶段
- 最近一轮模型输入摘要
- 最近一轮工具输出
- 当前是否在等待工具结果
- 失败时的最后上下文

### 9.3 用户可见与开发者可见分层

- 用户默认看到“可读摘要版”，保证简洁。
- 调试视图可展开“完整结构化轨迹”，用于排障。

## 10. 后端实现建议

### 10.1 执行上下文构建器

建议新增一个上下文构建模块，负责：

- 查询任务最近的步骤、模型调用、消息、工具结果
- 按阶段拼装结构化上下文
- 根据长度策略做裁剪或摘要
- 过滤敏感信息

### 10.2 工具调用闭环

当前工具执行逻辑已具备雏形，后续应保证每轮工具调用都记录：

- 工具名
- 参数
- 调用时间
- 返回结果
- 返回结果摘要
- 结果是否被模型采纳

### 10.3 上下文压缩

建议使用两级压缩：

- **短期上下文**：保留最近 N 个步骤与工具调用原文
- **长期摘要**：保留更早阶段的结构化摘要

---

## 11. 安全与合规

- 不展示也不落库敏感密钥明文。
- 工具输出中若包含私密内容，需脱敏后再进入用户可见视图。
- 模型可见轨迹中也应避免直接暴露机密凭据。
- 若未来需要展示“思考过程”，应仅展示产品定义的结构化执行轨迹，而非未经约束的内部推理草稿。

---

## 12. 验收标准（AC）

- AC1：任务运行时，模型下一次调用前能拿到上一轮的结构化上下文。
- AC2：工具调用链路可在任务详情页完整展开，能看到工具名、参数、结果和后续影响。
- AC3：多 Agent 场景中，各阶段能继承同一条轨迹，不会丢失前序步骤。
- AC4：任务失败后重试，模型能看到失败原因与失败前上下文。
- AC5：上下文过长时，摘要机制生效，模型仍能继续执行。
- AC6：前端可实时刷新轨迹视图，无需手动刷新页面。

## 14. 风险与待定项

### 风险

- 轨迹过长导致模型上下文膨胀。
- 工具输出过多导致前端和数据库膨胀。
- 若把所有内部过程都直接展示，容易造成 UI 噪音和安全风险。

### 待定项

- 是否新增独立 `TaskTrace` 表，还是先沿用现有表拼装。
- 轨迹摘要使用规则压缩还是模型压缩。
- 用户默认视图是否显示完整工具参数。
- 是否为不同 Agent 提供不同的轨迹可见粒度。

## 15. 与现有系统的关系

本 PRD 建立在当前已有能力之上：

- `backend/app/core/orchestrator.py` 已负责任务编排、步骤记录、模型调用和工具循环。
- `backend/app/schemas/task.py` 已有任务步骤和模型调用的返回结构。
- `backend/app/api/v1/endpoints/tasks.py` 已能返回任务详情、步骤和模型调用。
- 现阶段需要补齐的是：**把这些信息变成模型下一轮调用可直接消费的执行上下文**，并在前端形成一条清晰的轨迹视图。

---

## 16. 结论

该需求的核心不是“让模型真正暴露隐式思维”，而是把任务执行过程工程化为一条**可见、可追踪、可回灌、可恢复**的执行轨迹。

这样做可以同时满足：

- 模型执行时“看见自己已经做了什么”
- 工具调用链条透明
- 任务失败后可恢复
- 前端和后端都可审计
- 后续可扩展到更复杂的多 Agent 编排
