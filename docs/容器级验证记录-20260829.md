> 对象：C-170《独立 Worker 与事件总线链路启用》的容器实跑 AC（此前《AB与冒烟测试记录-20260828》§5 明确标注 AC1/AC4/AC8 未覆盖）。
> 环境：Docker Engine 29.6.2，`docker compose up -d --build`。

## 1. 发现的两个真实缺陷（并已在本次修复）

### 缺陷 A：容器模式启动崩溃（→ 提交 `2567b98`）
- `docker-compose.yml` 的 `DATABASE_URL: ${DATABASE_URL:-postgresql…}` 被宿主 `.env` 的 `DATABASE_URL=sqlite+aiosqlite:///./data/agent_console.db` 插值覆盖 → postgres 服务被旁路，backend 与 worker 两容器并发 `init_db()` 跑 `alembic upgrade head` 对同一 sqlite 文件竞争 → `table already exists`，backend `exited(3)`、worker `Restarting`。
- **修复**：容器 URL 改用新变量 `COMPOSE_DATABASE_URL`（对齐既有 `COMPOSE_REDIS_URL` 惯例，默认指向 `db`）；新增一次性 `migrate` 服务独占迁移，`backend`/`worker` 以 `service_completed_successfully` 等待其完成；应用内 `init_db()` 保留为幂等空转，兼容 `start-local.bat` 无 compose 的独立运行。

### 缺陷 B：僵尸队列条目（→ 提交 `4ccb5a4`）
- 容器实跑 AC4 时观察到：入队任务被 worker 领取（attempt 0→1）执行失败后，条目回到 `queued` 却再无被领取、也非终态。根因：`claim_next` 仅匹配 `Task.status == PENDING`，而 `run_task` 已把任务置 `FAILED`，重入队的条目成为不可领取的僵尸。
- **修复**：`TaskService.fail` 新增 `retry` 开关；worker 对「编排器已终结」的返回用 `retry=False` 直接落 `dead`，异常分支（任务可能仍 pending）保留有界重试。补 2 个回归测试（根因记录 + 修复坐实）。

## 3. 未覆盖项（诚实标注）

- **AC4「任务跑到 completed」**：本机 `DEEPSEEK_API_KEY` 为空，任务在模型调用处失败，队列条目落 `dead` 而非 `completed`。但「worker 跨进程领取并结算队列条目」的核心行为已证（`queued→leased→dead`，attempt 不异常累加）。完整 `completed` 闭环需在有 LLM 密钥的环境补验。
- **AC5/AC6**：AC5（结果等价）依赖 completed 闭环，同上受限；AC6（inline 回退）已在单元层覆盖（`test_task_recovery.py`），未额外起 inline 容器。
- 验证残留：postgres named volume 与宿主 sqlite 内含探针任务（运行时数据，未入 git）。宿主旧 `./data/agent_console.db`（9 表、无 alembic_version 的陈旧文件）已备份为 `agent_console.db.bak-20260829`，容器化 sqlite 迁移不再复用该脏文件。
