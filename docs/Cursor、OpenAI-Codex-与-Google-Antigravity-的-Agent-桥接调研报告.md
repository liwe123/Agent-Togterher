Cursor、OpenAI Codex 与 Google Antigravity 的 Agent 桥接调研报告

作者：Manus AI
检索与核验日期：2026-08-19（GMT+8）
调研对象：Cursor、OpenAI Codex（重点为 CLI/IDE）、Google Antigravity（用户所称“anti-gravity”按此解释）

执行摘要

三者之间最可靠的桥接方式，不是试图让其中一个 IDE 完全控制另一个 Agent，而是把协作拆为四层：各客户端共享同一个可信 MCP 工具层；每个执行 Agent 在独立 Git worktree 和短生命周期分支中工作；通过 Git、CI 与 PR 传递可合并的产物；只有在确有必要时，才引入第三方的“Agent-as-a-tool”桥或异步消息协调层。该设计可保留每个产品原生的审批、沙箱、凭证和模型选择，同时将改动冲突、供应链风险与不可审计的自动委派降到较低水平。1 2 3 4

  核心结论：MCP 是“共享工具/上下文协议”，不是“Agent 控制协议”。 Cursor、Codex 与 Antigravity 都有官方 MCP 客户端/宿主能力，但现有一手资料不能证明三者之间存在官方的、通用的 Agent-to-Agent 远程控制协议。将“都支持 MCP”直接等同为“可以安全地互相驱动”是常见误解。1 2 3

对于个人与小团队，推荐从“共同 MCP + 独立 worktree + PR 审核”起步；它覆盖大多数工具共享和多人并行编程情景。若确需由 Cursor 或 Antigravity 发起对 Codex 的专项复核，可在受控本机上评估 codex-bridge 一类第三方 stdio MCP server，但必须视作能够启动 Codex CLI 的本地代码执行组件，而非官方产品集成。5 对三名以上 Agent 的长任务，可考虑 mcp_agent_mail 型协调层管理消息与路径意图；其价值在于异步协调与审计，不在于替代 Git 隔离或人工合并审核。6

1. 范围、证据标准与关键边界

本报告的“桥接”包括四件不同的事：让多个 Agent 使用同一工具或数据源；让一个 Agent 把另一 Agent 当作可调用工具；让多个 CLI Agent 并行完成子任务；以及让多个 Agent 通过任务、消息和 Git 异步协作。前两者都可能用 MCP，但权限模型、失败模式与治理成本完全不同。报告仅把官方文档、官方代码库、MCP 规范作为能力结论的主证据；第三方 GitHub 项目只作为可审计候选，并按其维护、依赖与安全边界降级处理。

所谓“全网调研”在这里指覆盖公开可访问的中英文官方文档、MCP 规范、活跃开源实现及其源代码线索；它不宣称穷尽互联网或替代对目标版本、订阅、地区可用性和企业策略的上线前复验。文档功能演进较快，尤其是 Antigravity 的产品版本、MCP 传输与第三方桥接器，部署前应以相同链接再次核验。

2. 三方官方能力与互操作矩阵

三者的共同交集是本地 stdio 与远程 Streamable HTTP。因此，若一项共享服务要同时服务 Cursor、Codex 与 Antigravity，应优先实现 Streamable HTTP；如果只给单台开发机使用，则应优先选择受控 stdio。Cursor 与 Antigravity 另列出 SSE 支持，Antigravity 还列出 WebSocket；Codex 官方 MCP 页只列出 stdio 和 Streamable HTTP，故不要为三方共同服务选择 SSE 作为唯一传输。1 2 3

Cursor 官方文档称其支持 tools、prompts、resources、roots、elicitation 与 MCP Apps，并可用 mcp.json 连接本地或远程 server。企业还可对本地命令、远端 URL 和具体工具实施 allowlist，并为本地 command server 设定网络模式。它因此适合作为共享工具层的客户端，但这不意味着它本身对外暴露一个可由其他 Agent 调度的 Cursor Agent server。1

Codex 官方文档确认 CLI 能在本机仓库中检查、编辑、运行命令，并可用 codex exec 进入重复性脚本或 CI 工作流；MCP 专页则确认本地 stdio 和远程 Streamable HTTP 的接入，以及 OAuth、Bearer token 和项目级受信任配置。Codex 的 subagents 是其自身会话内部的委派能力，不能被表述为 Cursor 或 Antigravity 可以直接远程调用的跨产品 API。2 3

Antigravity 官方 MCP 文档提供 IDE、CLI 与 SDK 的配置入口。其 CLI 文档对远端连接要求使用 serverUrl，而不是 Cursor/Codex 文档中常见的 url 字段；这是一项容易造成配置失败的非兼容细节。其权限文档也表明，未配置的 MCP 和 command 默认 Ask，适合作为有人审阅的协调/开发端，但工作区内读写仍应依托 worktree 缩小影响面。4 7

3. 四种可桥接模式

3.1 模式 A：共享 MCP 工具层——默认方案

该模式让 Cursor、Codex 和 Antigravity 以各自的官方方式连接同一类 MCP server，例如 GitHub、Jira/Linear、文档检索、数据库只读查询、浏览器自动化或内部服务。每个客户端依旧自行选择何时调用工具；没有任何 Agent 被另一个 Agent“托管”。这既保留平台差异，也将跨产品共性沉到可治理的服务接口上。1 2 3

    sequenceDiagram
        participant D as 开发者
        participant C as Cursor / Codex / Antigravity
        participant M as 可信 MCP Server
        participant S as Git、工单、文档或内部服务
        D->>C: 给出任务与审批边界
        C->>M: 按本客户端配置认证并请求工具
        M->>S: 以最小服务身份执行
        S-->>M: 结构化结果
        M-->>C: 工具结果
        C-->>D: 展示变更、命令或审批卡

优点是官方支持范围最清楚、可逐个客户端撤销、服务端容易做审计。缺点是不能传递另一个 Agent 的私有会话、记忆或模型能力。团队应接受这一限制：把任务说明、结构化产物、Git diff 和测试结果当成跨 Agent 的“公共上下文”，而不是试图共享隐式聊天记录。

3.2 模式 B：Agent-as-a-tool——专项使用，不作为默认

eLyiN/codex-bridge 是代表性第三方：它将本地已认证的 Codex CLI 包装为 MCP tools，使 MCP 客户端可发送查询、文件内容或批量任务。仓库以无状态、默认 90 秒超时为设计，且提供可改变工作目录和通过 stdin 输送内容的接口。5 这可让 Cursor 或 Antigravity 把“请 Codex 评审这个 diff”作为一个工具动作，但本质上是主 Agent 触发本机程序并把工作区内容交给 Codex。

因此，模式 B 应至少满足四条前置条件：桥接器固定在受控版本并完成源码/依赖审查；调用工作目录必须限定在登记的 worktree 根目录内；Codex 保持 workspace sandbox、网络关闭或最小 allowlist；上游 Agent 不得获得跳过 Git/trusted-directory 检查的默认权。桥接器的 CODEX_SKIP_GIT_CHECK 只适合临时受控诊断，不能进入共享默认配置。5 该模式推荐用于只读设计评审、独立复核或有明确输入输出的子任务，不推荐用于“无限递归地让 Agent 互相写代码”。

3.3 模式 C：CLI 编排 + Git worktree——并行实施的主力方案

Git 官方将 worktree 定义为同一仓库附连的多个工作目录，可同时检出不同分支，且各自拥有独立的 HEAD 与 index。Git 默认阻止同一分支被同时检出到不同 worktree，这个约束正好帮助避免多个 Agent 误写同一分支。8 因此，可以由一个薄编排脚本、CI pipeline 或人工任务板分配任务，而 Cursor、Codex、Antigravity 任意一方都只对其 worktree 读写。

建议的运行规则是：主仓只用于计划、任务拆分和最终集成；每项任务创建 agent/<任务号>-<职责> 分支与对应 worktree；每个 Agent 输出 diff、测试命令、测试结果、风险说明；CI 在合并前执行；人类或专用审阅 Agent 仅对 PR/commit 评审，避免直接在执行树内做大范围改写。完成后，使用正常的 git worktree remove 清理干净工作区，而不是手工删除目录遗留管理记录。8

3.4 模式 D：异步协调层——多 Agent 长流程的可选增强

MCP Agent Mail 自述为基于 FastMCP、Git 与 SQLite 的协调层，提供临时身份、收发消息、可搜索历史与咨询性 file reservation。其仓库在检索日显示活跃维护，并附有 Codex、Cursor、Gemini 等配置线索；不过它仍是第三方，且仍在主动开发中。6 该类服务应被理解为“任务意图与消息总线”，而不是文件锁、身份边界或 Git 合并系统。

若采用，服务应先仅监听 loopback 或企业私网，Agent 使用独立注册身份，附件路径默认禁止绝对路径，消息保留期与访问人群明确记录。必须将协调服务的数据库、Git 归档和备份视为可能包含源代码片段、任务细节和内部决策的敏感系统。对两名 Agent 的短任务，Git issue、PR 描述和共享 TASK.md 往往足够；不要为了“显得多智能体”过早增加一个持久服务。

4. 可复制的配置骨架与注意事项

以下示例刻意不包含真实 token，且只表现三方连接同一个远端服务时各自的字段差异。部署时应优先使用 OAuth/组织密钥管理；若使用环境变量，确认各客户端当前版本对该字段的插值语法，避免把机密写入 Git。Cursor 文档明确支持对 url、headers 等使用变量插值；Codex 对远端 token 提供环境变量字段；Antigravity 文档明确提供 OAuth/ADC 和 headers，但本报告不把未在该页确认的字符串插值视为通用语法。1 3 4

5. 三套参考架构与选择建议

架构 I：个人开发者的本机最小方案

个人可将 Cursor、Codex 与 Antigravity 都连到少量只读或低权限 MCP server；开发任务以一项一个 worktree 运行。Cursor 适合作为交互式编辑端，Codex CLI 适合运行有明确输入输出的审查/测试脚本，Antigravity 可作为另一编辑或计划端；选择哪一个担任“主控”不影响隔离原则。将网络保持关闭，只有需要检索或远端 MCP 时按会话打开精准允许。

  任务              TASK.md 或 Git issue，写清验收与允许路径   每个 Agent 可得到相同显式任务包   只靠口头聊天或隐式会话记忆分工

  执行              一个任务一个 worktree/分支                 Agent 仅更改所属目录与分支        两个 Agent 同时写主工作区

  工具              共同只读 MCP，如 docs/GitHub 查询          有可验证的工具调用记录            安装来源不明的 marketplace server

  整合              本地测试 + diff 审阅 + 小提交              失败可回滚、改动可解释            允许 Agent 自动推送或直接合并主分支

架构 II：小型团队的 Git/CI 协作方案

团队应将共同 MCP server 置于受控内部端点，分别为开发者、CI 与 Agent 签发不同服务身份。任务系统创建分支和 worktree，Agent 在容器或受限用户权限下执行，结果以 commit/PR 进入 CI。任何“Agent 互调”最多是 PR 前的二次审阅步骤，不能跳过测试和 reviewer。

该架构的关键是把“执行权”和“合并权”分开：Agent 可以创建 diff，CI 可以报告测试，只有受保护分支的合并门禁才决定代码进入主线。即使第三方桥接器或某个模型做出了错误命令，也被限制在分支、工作区和审批范围内。8 9

架构 III：企业受控/敏感代码方案

对于内部代码、受监管数据或生产凭证，应先满足三项条件再考虑桥接：远端 MCP server 使用组织 OAuth/服务身份并在 allowlist 内；Agent 在受管端点或隔离容器工作，网络默认关闭并只允许必要域名；日志、审批、软件物料与数据留存满足企业策略。Cursor 可使用企业 MCP allowlist 和网络模式；Codex 可结合 workspace sandbox、network proxy 与域名规则；Antigravity 可用 Deny > Ask > Allow 规则对 MCP、命令和 URL 分类设置。1 7 9

企业默认不建议部署未经审计的第三方 Agent bridge，也不建议让任何 Agent 拿到生产云管理员凭证、全部仓库读权限或不受限网络。对于确有价值的 bridge，应通过一次性受限任务、专门技术账户、只读凭证、域名 allowlist、成本阈值、不可变审计日志和隔离临时 worktree 进行评估。

6. 安全、成本与运维治理

MCP 官方安全资料覆盖 confused deputy、token passthrough、SSRF、本地 MCP server compromise、OAuth URL 验证、stdio proxy、localhost redirect URI 与 scope minimization 等风险。这意味着“连接成功”只是开始：一个桥接 server 可能把模型指令、代码内容、网络请求和令牌处理聚集到同一执行链中。10 其中 Codex 还会读取 MCP 初始化返回的 instructions 作为 server-wide guidance，因此第三方 server 的文本同样进入 Agent 的指令面，应审查、最小化并与项目规则隔离。3

Codex 本地默认网络关闭，workspace-write 自动模式限制在活动工作区；其网络代理只有在网络启用且代理功能同时启用时才会实施域名限制。因而“写了一张域名 allowlist”并不等于“网络已安全受控”，必须同时验证实际 sandbox 和代理状态。9 Antigravity 的默认规则把未配置 MCP/command 置于 Ask，但项目内文件读写可自动允许；因此工作区本身必须是独立 worktree，而不能是含所有敏感资产的用户主目录。7

7. 30 分钟最小可行落地路径

下列路径不要求立即安装任何第三方 bridge，目标是先证明三类客户端能在相同项目治理下安全协作。

1.  创建一个无敏感数据的示例仓库，编写 TASK.md，其中列明允许的目录、测试命令、禁止操作、验收条件和预计预算。为每个子任务创建独立分支和 worktree；不要在主 worktree 中同时运行多个 Agent。8
2.  选择一个团队可审计的、只读或低副作用 Streamable HTTP MCP server。分别按 Cursor、Codex、Antigravity 的项目级配置接入；Cursor 使用 url，Codex 使用 TOML url，Antigravity 使用 serverUrl。先不配置全局 server。1 3 4
3.  保持三端的 MCP tool 在 Ask 状态。让三个客户端只完成“读取任务、查询同一文档/工单、输出各自实施方案”的无写入试验，核验客户端、认证、日志和停止机制。
4.  只选一个 Agent 在其 worktree 内执行小改动，另一个 Agent 仅通过 diff/测试结果做只读审阅。执行 Agent 不得拥有合并主分支的权限；审阅意见以 PR/issue 落盘。
5.  运行测试、人工审阅 diff，再合并。记录该任务的配置版本、调用日志、测试结果与失败原因。只有当这一闭环稳定后，才评估添加 Codex bridge 或 Agent Mail。

  停止条件： 若需要绕过 Git trusted directory、关闭 sandbox、开启全网网络、把生产 token 写入配置文件，或让一个 Agent 自动批准另一个 Agent 的破坏性操作，应停止实施并回到更低权限的模式。这些不是“集成摩擦”，而是风险边界被突破的信号。

8. 决策结论

如果你的目标是让 Cursor、Codex、Antigravity “一起干活”，最值得优先搭建的是共享 MCP 工具层 + worktree/PR 协作层。这既是三方官方能力的最大交集，也有最清楚的升级路径。对于复杂任务，可再添加受控的 CLI 编排；对于长周期多 Agent，可再添加异步协调服务；而直接 Agent 互调应被视为一次经过安全设计的特权能力，而不是默认架构。
