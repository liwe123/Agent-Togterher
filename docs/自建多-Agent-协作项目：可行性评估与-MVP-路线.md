自建多 Agent 协作项目：可行性评估与 MVP 路线

作者：Manus AI
评估日期：2026-08-19（GMT+8）
默认假设：个人或小团队的内部研发工具；先服务一个 Git 仓库、2–4 个并发任务；以 Cursor、OpenAI Codex、Google Antigravity 等编码 Agent 为运行时，不以多租户 SaaS 为第一阶段目标。

结论

你的自建多 Agent 协作项目技术上可行，并且值得做，但首版不应被定义成“让多个 Agent 自主结盟并自动交付代码”。更准确且可交付的产品定位是：

  一个面向 Git 代码仓的 Agent 控制面：把任务拆成可审阅的工作包，为每个工作包调度一个隔离的编码 Agent，聚合状态、权限、成本、CI 和 PR，并把合并权留给人。

这条路径具备现实基础。Codex 可以在终端和脚本/CI 中运行并接入 MCP；Cursor CLI 已提供可由自定义客户端通过 stdio + JSON-RPC 驱动的 ACP；Antigravity CLI 提供非交互的 headless 模式及 JSON/NDJSON 输出。三者不需要共享私有会话，也可以被统一抽象为“可启动、可观测、可取消、可能要求审批的 runtime adapter”。1 2 3

真正的护城河不是并发调用多个模型，而是可靠的任务状态机、worktree 隔离、权限与预算控制、审阅闭环以及对异构 runtime 的可演进 adapter 层。开源 Agent Orchestrator 的设计也印证了这一点：它将“一个任务、一个 Agent、一个隔离 workspace”作为 worker 单元，把项目级规划/委派与具体实现/测试/PR 分开。4

1. 你真正要构建的是什么

建议把系统分成两个角色，而不是让所有 Agent 都彼此对话。上层是控制面，负责把用户目标转成任务包、维护任务生命周期、选择 runtime、收集日志、生成审批请求、聚合测试和 PR 状态。下层是执行面，每次只执行一个任务：一个 worktree、一个分支、一个 Agent 进程、一组最小权限凭证与一个可取消的运行句柄。

这种分层比“多 Agent 群聊”可靠得多。Cursor ACP 需要客户端回应权限请求，否则工具执行会阻塞；Antigravity headless 将结果、诊断和流式事件通过不同通道输出；Codex 有自己的沙箱、审批与 MCP 配置。你的控制面要承认这些差异，并将它们转化为统一事件，而不是伪造一个看似一致、实际不可控的 API。1 2 3

2. 三条可选路线

下面的路线都可行。首选应由你的目标决定，而不是先被某个框架或云服务绑定。

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  路线                               适用场景与权衡                                                                                                                                                  成本                                               搭建复杂度
  ---------------------------------- --------------------------------------------------------------------------------------------------------------------------------------------------------------- -------------------------------------------------- -----------------------------
  A. 本机优先控制面                  控制面和 worker 跑在开发者电脑，直接复用本机已登录的 CLI、Git 和 IDE 环境；代码与凭证不必离开机器。缺点是机器须在线，不适合跨时区后台执行。                     额外云成本可为零；仍承担模型/订阅与 CI 成本。      低—中；推荐 MVP

  B. 受管看板 + 本机 worker          浏览器统一显示任务和审批；每位开发者机器部署一个配对 worker，真正执行 Cursor/Codex/Antigravity 与 worktree。比 A 更利于团队，但需要设备配对、身份和事件通道。   控制面可先低成本托管；模型成本仍按实际运行产生。   中；适合团队试点

  C. 中央调度 + 隔离远程 worker 池   面向 24×7、远程执行、自定义 CLI 或容器隔离。工程能力最强，但需要镜像、网络出口、密钥、资源配额、重试和运维。                                                    计算与存储随并发增长；需要预算与用量告警。         高；仅在 A/B 证明价值后采用
  -----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

对于轻量、常驻的控制面，受管单进程服务可支持后台队列、长连接和实时事件，但资源上限为 1 vCPU/512 MB；满载 24×7 的计算费用上限约为 $37.50/月，另有每月 $10 的使用额度，且按实际资源用量计费。它适合任务编排与看板，不适合在同一进程中运行不受信的代码 Agent。5 若确实需要 Docker、系统级隔离或更多资源，再使用独立的持续计算节点；这类环境应具备自动重启、最小开放端口、出站控制和备份策略。6

3. MVP 的最小功能边界

首版应该只处理一个仓库、一种任务类型、一条审阅闭环。建议优先完成以下模块，而不是做炫目的“自治 swarm”。

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  模块                    MVP 必须具备                                                                                                                      首版不做
  ----------------------- --------------------------------------------------------------------------------------------------------------------------------- --------------------------------------------------
  任务包                  目标、验收条件、允许路径、测试命令、预算、依赖与负责人                                                                            从模糊自然语言无约束地产生大量子任务

  状态机                  Draft → Queued → Provisioning → Running → WaitingApproval/Blocked → Validating → ReviewReady → Merged/Rejected/Cancelled/Failed   无上限重试或靠聊天记录推断真实状态

  Runtime adapter         先支持 Codex CLI + Cursor ACP；Antigravity headless 作为第三个 adapter                                                            一开始覆盖十几种 Agent 或追求完全相同的能力集

  隔离                    一任务一 git worktree、一分支、一进程、一个可写根目录                                                                             多个 Agent 共写同一工作目录或主分支

  审批                    写权限任务启动、网络/高风险 MCP、合并三类关卡                                                                                     默认自动批准、Agent 自我批准、无记录的控制台操作

  结果                    diff、commit、测试命令与结果、PR 链接、失败原因、运行摘要                                                                         自动将不透明会话记录视作可审计交付物

  观测                    事件流、取消、超时、租约心跳、简单成本/时长计量                                                                                   首版构建复杂的全链路计费系统
  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

这里最关键的产品选择是：规划器只能提出任务包和依赖，worker 才能写代码；worker 可以生成 PR，但不能合并受保护分支。 这延续了成熟控制平面的职责切分，也避免一个“总 Agent”同时拥有规划、执行、审阅和发布权。4

4. Adapter 设计：不要统一一切，要统一事件

请为每个 runtime 维护一份 Capability 声明，而不要仅靠字符串名称区分。最少字段包括：是否支持会话恢复、是否支持结构化流、是否支持取消、是否会发权限请求、是否有 read-only/plan 模式、是否支持 MCP、是否可报告 token/用量、认证前置条件和安全默认值。

  Runtime           可直接利用的官方能力                                                                                   Adapter 的职责                                                                   MVP 风险
  ----------------- ------------------------------------------------------------------------------------------------------ -------------------------------------------------------------------------------- -------------------------------------------------------------
  Cursor            ACP 支持 stdio、JSON-RPC、session、新建/加载、流式 update、权限请求与取消；有 plan/ask/agent 模式。2   进程管理、JSON-RPC 驱动、session 映射、permission event 转审批、取消与日志归档   不能无响应地忽略权限事件；ACP 对团队级 MCP 有限制。2

  Codex             本地终端编码 Agent，可调用 codex exec 做脚本/CI 工作流；支持 MCP、权限和工作区 sandbox。1              prompt/输出解析、运行目录固定、sandbox/权限配置、结果与命令日志归档              不得因自动化而放大写目录或开启全网网络。1

5. 风险边界：能做什么，不能承诺什么

MCP 可以连接工具和数据源，但不是安全的 Agent 控制总线。MCP 官方安全资料专门讨论 token passthrough、SSRF、OAuth URL 验证、本地 MCP server compromise 和 scope minimization；因此上游 Agent 的凭证不能被透明转交给下游 runtime 或第三方 server。7 Cursor、Codex 和 Antigravity 各自也提供 tool approval、sandbox 或 Ask/Deny/Allow 一类机制；控制面应显示并收集这些请求，而不是替用户统一回答“always allow”。1 2 8

  -----------------------------------------------------------------------------------------------------------------------------------
  风险                                MVP 的硬性处理方式
  ----------------------------------- -----------------------------------------------------------------------------------------------
  写入冲突                            通过 worktree/branch 隔离；文件租约仅作提示，不能替代 Git 保护。

  提示注入                            外部网页、Issue、MCP resource、server instructions 都是数据；不能改变任务包、权限或合并策略。

  凭证泄露                            每个 runtime/server 用独立最小 scope 身份；密钥不进 Git；禁止 token passthrough。

  成本失控                            每任务轮次、并发数、运行时长和预算上限；达到阈值自动 Blocked。

  重试引发重复写操作                  幂等任务键、租约/心跳、显式 checkpoint、可验证的恢复逻辑。

  自动发布或破坏性动作                保留人类审批；必须经受保护分支、CI 和 PR 审阅。
  -----------------------------------------------------------------------------------------------------------------------------------

6. 分四阶段验证，而不是一次性造平台

阶段 0：两天内验证“运行时适配”

用一个无敏感数据的示例仓库，手工创建两个 worktree。实现一个极薄的 CLI 控制器，只支持创建任务、分配 worktree、运行一个 Codex task、收集 stdout/stderr、保存 diff 和退出码。成功标准不是代码质量，而是可以可靠地取消、超时后回收、重启后识别孤儿 worker，并且不会改动主 worktree。

阶段 1：一周内验证“协作闭环”

加上 Cursor ACP adapter，支持把 Cursor 的 session/request_permission 映射到一个明确的 WaitingApproval 状态；加入任务包、事件日志、CI 触发和 PR 摘要。此阶段只允许两个并发 worker，所有网络/MCP 工具保持 Ask。成功标准是：两项独立任务能完成且改动不冲突；人可在看板中准确判断每项任务是否可审阅。

阶段 2：两至三周内验证“价值而非技术炫技”

加入 Antigravity headless adapter、依赖 DAG、预算/轮次上限、任务重试策略和简单的结果评分。安排 10–20 个真实但低风险的维护任务，对比“人工单 Agent”和“你的控制面”两种方式的交付周期、失败率、人工干预次数、CI 一次通过率和每个合并 PR 的运行成本。只有在可重复改善其中至少两项指标时，才扩大 Agent 数量或功能。

阶段 3：决定是否团队化/远程化

若团队确实需要共享看板和异地运行，再演进到“受管控制面 + 本机 worker”。只有当开发者电脑不能满足 24×7、Docker/自定义 CLI 或隔离 worker 池的硬需求，才把执行面迁到远程基础设施。不要先花时间自建远程集群，再寻找真实使用场景。

7. 最终建议

建议你采用以下路线：

1.  立项，但把首版定位为“受控多 Agent 开发控制面”，而不是自治软件公司。
2.  从本机优先开始，先实现 Codex CLI 与 Cursor ACP 两种 adapter；Antigravity 作为第三个验证异构 runtime 的对照组。
3.  以 worktree、状态机、审批和 PR/CI 为核心，而不是以聊天、群体辩论或复杂 planner 为核心。
4.  把“自动合并、全网访问、生产操作、无界递归子 Agent、多租户”全部推迟。
5.  用阶段 2 的真实任务数据决定产品是否继续扩大；如果没有可测量的交付效率或可观测性收益，及时止损，不要把工程复杂度误认为产品价值。
