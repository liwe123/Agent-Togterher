### 1.1 独立 Worker 进程是死代码

2. `docker-compose.yml` 加 `worker` 服务：`command: python -m app.worker`，`depends_on: db/redis healthy`
3. `start-local.bat` 增加一个窗口拉起 `python -m app.worker`
4. `backend/Dockerfile` 确认 `app.worker` 可被 `python -m` 加载

### 1.3 任务租约缺「续租」，回收只在 Worker 启动时跑一次

文档 P3-M3 承诺「建立任务**租约、续租**与失联回收机制」。实际：

| 能力 | 状态 | 证据 |
|---|---|---|
| 租约 claim | ✅ 原子 `UPDATE ... WHERE` 抢占 | `task_service.py:49-93` |
| **续租 renew** | ❌ **TaskService 根本没有 renew 方法** | `task_service.py` 方法清单只有 `enqueue / claim_next / complete / fail / recover / _finish` |
| 失联回收 | ⚠️ 有 `recover()`，但**只在 `run_worker()` 启动时调用一次**，运行中无定时 sweep | `worker.py:41-43` 启动即调；无循环 |

**缓解因素**：`claim_next` 用 `max(lease_seconds, candidate.timeout_seconds)` 算租约（`task_service.py:86-87`），`timeout_seconds` 默认 1800 秒，所以短任务不会出问题。**但超过 30 分钟的长任务仍会被误判失联并重复消费**，而 `MODEL_REQUEST_TIMEOUT_SECONDS` 默认 60s、多步编排任务很容易叠加超 30 分钟。

另外有一套**平行的租约体系**：`orchestrator.py` 用自己的 `execution_token` + `_renew_task_lease` 后台续租协程（`orchestrator.py:130-168`）。**两套租约互不同步**，是潜在的重复执行源。

**补完动作**：
1. `TaskService` 增加 `renew(item_id, lease_token, lease_seconds)` 方法
2. `worker.py` 的 `_consume_once` 里加一个和 orchestrator 类似的续租协程
3. `run_worker()` 主循环里每 N 秒调一次 `recover()`
4. 【架构决策】明确二选一：要么统一到 TaskQueueItem 租约，要么删掉 orchestrator 的 execution_token 租约。**现在两套并存是负债。**

## 9. 总体判断

**代码的真实完成度比文档谦虚、比预期高。** 20 张表、175 个后端测试、7 个完整业务页面、2 个可用的外部 Agent 适配器——这些是实打实的。全仓库只有 3 处 TODO 也说明代码整洁度不错。

**真正的问题不在"没写"，而在"写了没接上"。** Worker 进程、Redis 事件总线、快照同步这三块，代码质量都不差，但**部署编排和默认配置把它们全锁在关闭状态**。这不是能力问题，是"最后一公里"问题——补上去的成本很低（P0 三项加起来不到 50 行配置），但不补，文档里那三个「✅ 已达成」就是假的。

**给简历/面试的建议**：如果要讲这个项目，"实现了独立 Worker 进程"这句话现在**不能说**——它没被启动过。修完 P0-1 之后才可以理直气壮地说。
